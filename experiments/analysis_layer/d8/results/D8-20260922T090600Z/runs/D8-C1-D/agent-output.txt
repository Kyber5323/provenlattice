CFG 分析直接给出了答案。证据齐备。

## 结论

**`notify()` 的执行不依赖 `validate()` 的返回值；`persist()` 的执行依赖 `validate()` 的返回值（真值）。**

## 证据 1：源码（`pipeline/handle.py`，`handle` 函数，第 1–4 行）

```python
def handle(x):
    if validate(x):      # 第 2 行：条件表达式即 validate 的返回值
        persist(x)       # 第 3 行：位于 if 语句的 then 分支内
    notify(x)            # 第 4 行：位于 if 语句之外、分支合并之后
```

`persist(x)` 缩进在 `if` 块内 → 仅当 `validate(x)` 为真值时执行。`notify(x)` 与 `if` 平级、在其后 → 无论条件真假都会执行。

## 补充说明（严格语义）

`validate(x)` 在顺序上总先于两者被调用（第 2 行），因此“不依赖”指的是**不由其返回值做分支门控**：`validate` 返回假值/空值时 `notify` 照常执行。仓库自带的 fixture 说明（`README.md`）也与此一致：“handle.py | handle | **notify is unconditional (after merge); persist is conditional**”。

ANSWER: 在 `pipeline/handle.py` 的 `handle()` 中，`persist()` 位于 `if validate(x):` 的 then 分支内，**依赖** `validate()` 的返回真值；`notify()` 位于该 if 语句之后（分支合并点之后），在真/假两条路径上都会执行，**不依赖** `validate()` 的返回结果。CFG 证据：`explain-symbol pipeline.handle.handle --analysis cfg` 中 condition 节点（`if_condition`，字节 22–33 即 `validate(x)`）的 `"true"` 边唯一通向 persist callsite（字节 43–53，`resolved_symbol_id`=persist），`"false"` 边直连 merge；persist 与 false 边在 merge 汇合后由 `merge --next-->` 到达 notify callsite（字节 58–67，`resolved_symbol_id`=notify），故 notify 覆盖 entry→exit 的所有路径。
