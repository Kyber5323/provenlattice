# 01 · 为什么选择 CFG+DFG 的稀疏图

> 本篇回答：为什么不做完整 CPG？「稀疏」的判据是什么？砍掉的东西去哪了？
> 依据：设计文档 §2 / §9 / §14 / §18 / §25。

---

## 一、起点：AI 缺陷检测卡在一个具体的地方

大模型能读代码，但读的是**文本**。它能说「这段代码看起来没检查返回值」，却无法可靠回答：

- 这个指针在解引用之前，有没有可能已经被释放？
- 这个锁的获取顺序，在另一个文件里是不是反的？
- 这个从 `getenv` 拿到的字符串，有没有在进 `system()` 之前被校验过？

这类问题的共同点是：**答案不在任何一个文件里，而在跨过程、跨文件的事实里**。文本里没有这些事实。

于是自然的想法是：把代码变成图，让模型查图。

---

## 二、三条路，以及为什么选了第三条

| 路线 | 做法 | 问题 |
|---|---|---|
| **A. 纯文本 / RAG** | 把代码切块喂给模型 | 跨过程事实**结构性地拿不到**。检索再好也检索不出「另一条路径」 |
| **B. 完整 CPG** | AST + CFG + DFG + Call Graph + 类型统一成 Property Graph | 学术上完整，工程上撞墙（见 §三） |
| **C. 稀疏语义图**（本项目） | 只保留缺陷分析需要的控制流与数据流 | 需要回答「保留什么、砍掉什么」——本篇的主题 |

**怎么读**：这不是「B 做不到所以退而求其次」。C 是一个**不同的设计目标**：B 追求「程序语义的完整表示」，C 追求「缺陷证据的密度」。目标不同，最优结构就不同。

## 三、完整 CPG 的三个问题

设计文档 §2 列出三条，逐条给出本项目的实测支撑：

### 问题 1：空间放大

> 每个 statement、expression、identifier、literal 都可能成为节点。

**实测支撑**：libgit2-24（1,034 文件 / 299,134 行）建成后的存储构成——

| 表 | payload | 占比 | 行数 |
|---|---:|---:|---:|
| semantic_events | 99.96 MB | 35.0% | 182,227 |
| semantic_edges | 83.56 MB | 29.3% | 157,260 |
| raw_references | 40.76 MB | 14.3% | 89,438 |
| nodes | 30.12 MB | 10.6% | 14,452 |
| edges | 23.99 MB | 8.4% | 44,614 |
| 其余（shards / shard_edges / files / state） | 7.09 MB | 2.5% | — |

**怎么读**：**语义层两表合计 64.3%，是最大的体积项。** 这里有一个必须主动说清的反转——在**只有 Python 的小仓**上，raw_references 才是最大项（本仓 103 文件时占 50.3%，语义层只占 11.3%）。原因不是「没有语义层」，而是**那条路径不出 CFG**：事件层照常产出（12,583 行），但没有 WRITE / DEREFERENCE 点，语义层因此很薄。**语义层一旦建全，它自己就是体积。**

**这恰恰说明「稀疏」还做得不够。** 即使只保留缺陷相关的事件与边，仍然占 64%。根因是当前用 SHA-256 稳定 ID + 普通 B-tree 索引（设计原则 12），而设计原则 11 的 integer ID + CSR **尚未交付**——这是本项目最明确的一处已知取舍（见 §七 与 [08](08-答辩追问预案.md) Q7）。

口径：各表所有列 `length()` 之和，**不含页开销、索引与空闲页**，因此不等于文件大小。

**外推**（基数：本仓 10,115 行时实测，每千行 nodes 63.7 / edges 257.4 / raw_refs 2,475.5 / DB 2.77 MB）：

| 代码量 | nodes | edges | raw_refs | DB | update 前置内存 |
|---:|---:|---:|---:|---:|---:|
| 100 万行 | 63.7k | 257k | 2.48M | 2.6 GB | **4.0 GB** |
| 300 万行 | 191k | 772k | 7.4M | **7.8 GB** | **12.0 GB** |

**怎么读**：三条必须一起说的口径——① **基数只有一个 10k 行的样本，且是 reference 密度偏高的库代码**；② 该基数取自较早状态，本仓源码包此后已从 10,115 行增长到 16,087 行（31 个文件），外推值**未随之更新**；③ 真实工程仓会有偏差（C++ 头文件、生成代码、vendored 依赖会拉高）。**量级可信，具体值不可引用为承诺**。

这三条外推不是纸面推演，它们直接定义了阶段 0 要修的三个阻塞问题（P1 内存 / P2 硬崩溃 / P3 单文件体积），见 [05-实施过程](05-实施过程.md) §阶段 0。

### 问题 2：AI 并不需要全部语法细节

> AI 判断资源泄漏时，真正关心的是 `ALLOC → 分支 → RETURN / RELEASE`，而不是完整 AST 中所有括号、literal、binary expression。

**实测支撑**：阶段 6 交付的 8 个查询里，`taint_path` 在**两个真实仓上都返回 0 条候选**。它的 population（`input_to_sink` 边）是 redis 3,491 / llama 5,507 条——**事实是有的，但按「源 → 汇」的判据筛完之后一条不剩**。

**怎么读**：如果按「存了多少」来评价，这个查询是失败的。但它证明的是另一件事：**真正稀缺的不是事实，是判据**。把更多语法细节塞进图里，不会让这 3,491 条里多出一条真候选。

### 问题 3：查询噪声增加

> 缺陷检测需要的是高密度证据。把完整 AST 子图交给模型，会增加 token、检索和推理成本。

**实测支撑**：小世界效应——在 libgit2-24 的 14,452 个节点上，从**度最高的单个函数** `git_error_set`（度 723）出发做 BFS：

| 跳数 | 新增节点 | 累计覆盖 |
|---:|---:|---:|
| 1 | 723 | 5.0% |
| 2 | 2,773 | 24.2% |
| 3 | 6,412 | **68.6%** |
| 4 | 3,512 | 92.9% |
| 5 | 975 | 99.6% |
| 6 | 55 | **100.0%** |

**怎么读**：**从一个函数出发 6 跳，覆盖全部 14,452 个节点。** 3 跳就到 68.6%。这意味着无差别的 N-hop 扩展在任何真实仓上都迅速退化成「把整个图交给模型」——**那等于放弃了图**，还不如直接喂代码。这就是设计原则 13「用 Typed Query 而不是无差别 N-hop BFS」的实测依据（见 §六）。

## 四、「稀疏」的判据是什么——这是本篇的核心

**不是「尽量少存」，而是「由缺陷反推」。**

设计文档 §9 的标题就是这句话：**36 类缺陷驱动 Schema，而不是 CPG 驱动 Schema。**

> **口径登记**：设计文档写「36 类」，而 `defect-evidence-matrix-v1.md` 的标题写「9 大类 **38** 小类」。**两处不一致尚未对齐**；本知识库凡陈述**项目实际状态**时一律用 **38**，引用设计文档原文时保留「36」（见 [07](07-边界与未修缺口.md) §三）。

| | CPG 驱动 | 缺陷驱动（本项目） |
|---|---|---|
| 出发点 | 语法产生式：有哪些节点类型？ | 缺陷模式：要判这条，需要什么事实？ |
| Schema 形状 | 由语言决定，全语言统一 | 由缺陷清单决定，**用不到的不建** |
| 新增一种缺陷 | 通常不用改 Schema（本来就有） | **可能需要新增 Event 或 Edge 类型** |
| 代价 | 存储与噪声 | 覆盖面——**没展开的缺陷族就是没有** |

**怎么读**：右边那一列的最后一行是这套设计的**真实代价**，必须一起看：**38 类**缺陷里，本项目**登记了 13 个模式、展开了 9 个、交付了 8 个查询**（见 [04](04-缺陷查询与证据包.md)）。这不是没做完，是「缺陷驱动」这个选择的必然结果——**Schema 跟着缺陷走，没写的缺陷就没有对应的图**。

### 一个具体的反推例子

「竞态条件」（矩阵 1.1）需要判断：两个对同一变量的访问，是否可能并发执行且无保护。反推出的事实清单：

1. 这个变量**是什么**（声明身份、作用域、存储期）——否则两个方法各有一个局部 `n` 会被判成同一个 `n`
2. 谁**读**了它、谁**写**了它
3. 这些访问在哪个方法里（`EXECUTES_IN`）
4. 有没有锁保护（`PROTECTED_BY`）、是不是原子操作（`ATOMIC`）
5. 有没有可能并行（`MAY_PARALLEL`）

**注意第 1 条**：它**不是数据流事实，是符号表事实**——声明就在解析器已经读过的 AST 里，不需要任何推断。

**这条观察改变了整个项目的路线图**（见 [05-实施过程](05-实施过程.md) §阶段 4→5 的修订）。

## 五、稀疏到什么程度：不存 / 存 / 压缩

设计文档 §18 的三张清单，逐条对应到实现：

### 不存

| 不存 | 实现里的落点 |
|---|---|
| 完整 AST | `graph.py:28-45` 明确注释：parse cache **刻意不含 events 与 CFG**，AST 用完即弃 |
| 所有 Identifier / Literal / Expression | 只有进入词汇表或结构点的语法节点才发布为 Semantic Event |
| 完整 CFG 中间节点 | 只保留关键 Event 之间的 `CONTROL_REACHES` |
| 完整 DFG 中间表达式 | 只保留五类缺陷相关 value flow |
| 大量重复 source text | Event 只存 source span（行列），不存文本 |

### 存

稳定代码实体（Repository / Directory / File / Symbol）、缺陷相关 Event、高价值语义 Edge、Event source span、Evidence ID、必要 flags。

### 压缩

| 压缩手段 | 状态 |
|---|---|
| SHA ID → runtime uint32 | **未做**（当前用 SHA-256 稳定 ID，见 §七的代价） |
| event type → uint8/uint16 | **未做** |
| adjacency → CSR | **未做**（阶段 7 议题） |
| 冷证据分离 | **已做**（`raw_references` 独立表，见 [02](02-架构与数据模型.md)） |

**怎么读**：压缩这一列**大部分是设计意图，不是已交付状态**。当前交付的是「不存」和「存」两列，加上冷证据分离。整数 ID + CSR 在阶段 7 的路线图上，**别把设计文档当成交付清单读**。

## 六、砍掉的东西去哪了——三个不能丢的

稀疏的代价是「信息不全」。如果直接丢掉，图就会给出**自信的错误答案**。本项目的答案是：**不丢，但降级**。

### 1. 不确定的关系 → 证据，不是事实边

设计原则 9：**确定事实进入 Hot Graph；不确定关系进入 Evidence。**

- 确定的进 `semantic_edges`（如 `CONTROL_REACHES`）
- 不确定的**不造边**。典型例子：`MAY_ALIAS`（两个名字可能指同一对象）**只记录候选元数据，绝不创建 `ALIAS` 边**

**怎么读**：这条纪律的代价是**漏报**——`q = p; free(p); sink(q)` 这种靠别名传播的缺陷，如果两侧都没有事件，图里就是空的。这是**主动选择的漏报**，换的是「不会把猜测当事实」。

### 2. 原始引用 → 冷证据

设计原则 10：**raw_references 是冷证据，不参与常规多跳。**

它保存「解析阶段发现、但尚未被压缩成确定图边的原始引用证据」，按 `(file_id, start_line)` 联结。阶段 6 的 `taint_path` 就是靠它把 CALL 点还原到被调函数名的（覆盖率 redis 55,209/55,231、llama 206,662/208,128）。

**怎么读**：冷层的意义是**把 raw_references 挡在热查询路径之外**。查询不扫它，只在需要时按精确键取几行。

**这条的分量取决于仓**：raw_references 占库体积的比例，在 libgit2-24 上是 **14.3%**（§三 问题 1 的表），在**还没有语义层的小仓**上可以高到 **50.3%**。**语义层越薄，冷层分离越值钱**——这不是一句恒真的好处，是有条件的。

### 3. 完整图 → Evidence Bundle

设计原则 14：**给 AI 的是 Evidence Bundle，而不是整个图。**

AI 拿到的不是子图，是**结构化的证据包**：候选 + 三态判定 + 证据路径 + **缺失证据清单**（`missing_evidence`）。最后一项是关键——它明确告诉 AI「我缺什么才能确认」，把推断责任交回给 AI。

## 七、16 条核心设计原则（原文）

> 引自设计文档 §25。

1. 不做完整 CPG，只做缺陷导向的稀疏程序图。
2. Method-level Code KG 保留，作为全局骨架。
3. 增加 Semantic Event，作为真正的缺陷分析粒度。
4. AST 临时使用，不永久存储。
5. CFG 只保留关键 Event 之间的控制可达关系。
6. DFG 只保留缺陷相关 value flow。
7. 关键词从「Bug 判定器」变成「候选/事件发现器」。
8. 36 类缺陷反向决定 Schema。
9. 确定事实进入 Hot Graph；不确定关系进入 Evidence。
10. `raw_references` 是冷证据，不参与常规多跳。
11. 热拓扑使用 integer ID + CSR/adjacency。
12. 持久化继续保留 SHA-256 stable identity。
13. 缺陷检测使用 Typed Query，而不是无差别 N-hop BFS。
14. 给 AI 的是 Evidence Bundle，而不是整个图。
15. 复杂问题采用 Global Sparse Graph + Local Deep Analysis。
16. 保留 ProvenLattice 的确定性、三态证据、增量一致性和跨层知识能力。

**逐条状态**（哪些已交付、哪些是意图）：

| 原则 | 状态 |
|---|---|
| 1, 2, 3, 4, 5, 6, 7, 9, 10, 12, 13, 14, 16 | **已交付** |
| 8 | 部分：**38 类矩阵已定义**，登记 13 个模式 / 展开 9 个 / 交付 8 个查询 |
| 11 | **未交付**（SHA ID + 普通索引；CSR 在阶段 7） |
| 15 | **未交付**（Global Sparse Graph 已交付，Local Deep Analysis 未做） |

**怎么读**：第 12 条（SHA-256 stable identity）与第 11 条（integer ID + CSR）是**有张力的**——保 SHA 换确定性，代价是体积与遍历速度。本项目选了确定性，**这是一个可以质疑的取舍**，答辩时应当主动说明（见 [08](08-答辩追问预案.md) Q7）。

## 八、定位

设计文档 §26 的原文：

> **A deterministic, evidence-preserving, defect-oriented sparse semantic program graph for AI-assisted code analysis.**

> 面向 AI 代码缺陷检测的、确定性且保留证据与不确定性的稀疏语义程序图。

**它不是 Joern 的替代品**，核心指标也不是「存了多少 AST 节点」。它要提供的是：

- **确定性** —— 同一输入两次索引，语义表逐字节相同（见 [06](06-实验结果.md) §七）
- **证据保留** —— 每条候选都带可回溯的路径与行号
- **不确定性保留** —— 三态证据（resolved / ambiguous / unresolved），且**零升级**

**怎么读**：这三条是**可验证的承诺**，不是形容词。[06](06-实验结果.md) 给出了每一条的实测。
