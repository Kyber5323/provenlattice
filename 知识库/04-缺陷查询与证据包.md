# 04 · 缺陷查询与证据包

> 本篇回答：查询怎么工作？三态证据是什么？给 AI 的到底是什么？**工具为什么说自己不能确认缺陷？**
> 依据：设计文档 §13 / §14 / §15 / §16 / §21，以及 2026-09-30 实测。

---

## 一、为什么不用无差别 N-hop BFS

回顾 [01](01-为什么稀疏图.md) 的实测：在 libgit2-24 的 14,452 个节点上，从单个函数出发 **6 跳覆盖 100%**，3 跳就 68.6%。

设计原则 13：**缺陷检测使用 Typed Query，而不是无差别 N-hop BFS。**

| | 无差别 N-hop | Typed Query |
|---|---|---|
| 输入 | 一个节点 + 跳数 | **一个缺陷问题** |
| 输出 | 子图 | 候选 + 三态 + 证据路径 + **缺失证据** |
| 扩张控制 | 跳数（粗糙，且小世界下失效） | **判据**（每个查询自己的淘汰规则） |
| 淘汰 | 无 | **显式计数**（guard 5 / disjoint 4 …） |

**怎么读**：`get_subgraph(node, max_hops=N)` **仍然保留**给探索型 Agent（设计文档 §14 明写）。Typed query 是**增加**的一条路，不是替代。区别在于：缺陷检测不能靠「多跳看看」，要靠「按判据筛，并且说清筛掉了什么」。

## 三、三态证据

设计文档 §16：三态证据扩展到语义图。

| 状态 | 含义 | 判据（以 `null_flow` 为例） |
|---|---|---|
| `resolved` | **全部事实确定** | 声明级身份 + 无别名跳 + 该身份无任何 CHECK |
| `ambiguous` | **有不确定因素** | 有别名跳 / unknown 根身份 / 部分路径被守卫 |
| `unresolved` | **缺少必要事实** | 解引用点无声明 |

**三条纪律**：

1. **零升级**：不确定的事实**绝不**升级为 `resolved`。有专门的测试闸钉住（克隆阶段 5C 的断言）。
2. **`uncertain` 不进 precision 比值**，但在表内可见。
3. **空层报 `n/a` 而不是 `0.0`**——「这一层没有样本」与「这一层全是假阳性」是两回事。

**怎么读**：三态不是「置信度的三档」，而是**三种不同的认识论状态**：

- `resolved` = 「我知道，而且我知道我知道」
- `ambiguous` = 「我知道有这么回事，但有关键细节不确定」
- `unresolved` = 「我连基本事实都没有」

**这个区分是给 AI 用的。** `resolved` 的候选可以当强证据用；`ambiguous` 需要 AI 自己补上下文判断；`unresolved` 基本等于「这里有东西，但我不知道是什么」。**把它们混成一个分数，就丢掉了最有用的信息。**

## 四、给 AI 的是什么：Evidence Bundle

设计原则 14：**给 AI 的是 Evidence Bundle，而不是整个图。**

一个 bundle 包含（设计文档 §15）：

| 部分 | 内容 |
|---|---|
| **候选** | 缺陷类型、位置、主体身份 |
| **三态判定** | resolved / ambiguous / unresolved |
| **证据路径** | 可回溯的事件序列与行号 |
| **缺失证据** | **`missing_evidence`——我缺什么才能确认** |
| **缺失关系** | `missing_relations()`——图里没有哪种关系 |
| **淘汰记录** | `_elimination_record`——筛掉了多少、按什么理由 |

### 最关键的是「缺失证据」这一项

`null_flow` 的 `missing_evidence` 包括：

- `_MISSING_NULLABILITY` —— **哪些函数可能返回 NULL**（AI 侧 API 契约）
- `_MISSING_PARTIAL_GUARD` —— 部分路径的守卫语义

`error_handling` 的包括：

- `_MISSING_MUST_CHECK` —— **哪些 API 的返回值必须检查**（矩阵 9.1 明写这是 AI 侧 API 语义，不是图谱的活）

**怎么读**：这是本项目与「静态分析器」最根本的区别。一个传统分析器只会输出「第 42 行可能有空指针解引用」。本项目输出的是：

> 「第 42 行有一个解引用；它的值是第 38 行 `malloc` 的返回值；从第 38 行到第 42 行之间存在一条路径，该路径上**没有任何检查**；但**我无法判断 `malloc` 失败的可能性有多大**，也不知道这个函数的调用方是否已经保证了非空——**这两条是 AI 该补的**。」

**它把「我确认不了的部分」显式地交出去了。** 这就是下面这张表的含义。

## 五、最关键的一张表：`coverable_now` 全 False

**直接从代码实测**（`defect_matrix()`，无需开库）：

| 模式键 | 查询 | `coverable_now` | `candidate_coverable_now` | `missing_relations` |
|---|---|:---:|:---:|---|
| 1.1 | race_condition | **False** | True | EXECUTES_IN, MAY_PARALLEL, PROTECTED_BY, READS, WRITES |
| 1.3 | lock_order | **False** | True | ACQUIRES |
| 1.4 | lock_order | **False** | True | ACQUIRES |
| 3.1 | null_flow | **False** | True | CHECKS, DOMINATES_CHECK, RETURNS |
| 4.1 | resource_lifetime | **False** | True | PRODUCES, RELEASES, RETURNS |
| 4.2 | double_free | **False** | True | MAY_ALIAS, RELEASES |
| 4.3 | use_after_free | **False** | True | CHECKS, MAY_ALIAS |
| 4.5 | — | **False** | False | — |
| 4.6 | resource_lifetime | **False** | True | ACQUIRES, PRODUCES, RELEASES |
| 9.1 | error_handling | **False** | True | CHECKS, PRODUCES |
| 9.2 / 9.3 / 9.4 | — | **False** | False | — |

**合计：`coverable_now` 为 True 的：0 / 13。`candidate_coverable_now` 为 True 的：9 / 13。**

### 这张表怎么读

`coverable_now` 问的是：**「这个模式现在能被确认吗？」** 13 个模式**全部回答「不能」**。

`candidate_coverable_now` 问的是：**「这个模式现在能生成候选吗？」** 9 个已展开的回答「能」。

**这不是矛盾，这正是设计意图。** 源码注释写得很清楚：

> 1.1 answering "no" and "yes" at once is the point, not a contradiction.

**它在说：**

> 我能给你**值得看的地方**，但我**不能告诉你那里有 bug**。确认需要的东西（哪些 API 必须检查返回值、哪些函数可能返回 NULL、两个名字是否真的指同一个对象）**不在代码里，在图里也推不出来**。

**这是本项目最重要的一个主张，也是最容易被误读的一个。** 答辩时应当主动说：

> 这个工具**不是缺陷检测器**。它是**缺陷候选生成器 + 证据包构造器**。它把「在 69 万行里找值得看的 100 个地方」这件事从不可做变成可做，把「这些地方到底有没有 bug」留给 AI 和人工。

## 六、查询成本（实测，redis-50 / 325 文件 / 24 万行）

通过 `GraphQuery` 交付路径测量（与 CLI `--type <name>` 同一条路），默认 limit 下：

| 查询 | 耗时 | 返回候选 | 缺陷键 | 二次运行一致 |
|---|---:|---:|:---:|:---:|
| `taint_path` | **4.7 s** | 0 | — | ✅ |
| `error_handling` | 4.7 s | 20 | 9.1 | ✅ |
| `null_flow` | 4.8 s | 20 | 3.1 | ✅ |
| `lock_order` | 4.9 s | 1 | 1.4 | ✅ |
| `resource_lifetime` | 7.6 s | 20 | 4.1, 4.6 | ✅ |
| `race_condition` | 7.8 s | 20 | 1.1 | ✅ |
| `double_free` | **64.8 s** | 20 | 4.2 | ✅ |
| `use_after_free` | **124.5 s** | 20 | 4.3 | ✅ |
| **八个分别跑合计** | **223.8 s** | | | |
| **`all` 一次跑** | **204.2 s** | 20 | | |

**怎么读**：四件事。

1. **确定性**：八个查询全部二次运行返回**逐位相同**的证据 ID 序列。这是可复现性的直接证据。
2. **成本分布极不均匀**：`use_after_free` 124.5 s 是 `taint_path` 4.7 s 的 **26 倍**。主导项是 `find_paths` 的路径枚举（见 [03](03-稀疏CFG与DFG.md) §六）。
3. **`all` 的语义在本阶段变了**：从 3 个查询变成 8 个，**成本上升一个数量级**。这是一个会打破既有调用者的行为变更，已登记。
4. **这些数字在交付态下测得**（契约 + 参数绑定开着），描述的是用户实际付的代价。

**已登记的待优化项**：`use_after_free` / `double_free` 的 `find_paths` 枚举是明确的性能瓶颈，**修复方案已知但未实施**（见 [07](07-边界与未修缺口.md) §五）。

## 七、AI 与静态规则的职责边界

设计文档 §21 划的界，逐条对应到实现：

| 层 | 负责 | 本项目对应 |
|---|---|---|
| Parser / deterministic analyzer | 语法事实 | Tree-sitter + 声明索引 |
| Rule / semantic extractor | 事件识别（**候选发现器，不是判定器**） | 词汇表 `cpp.toml` |
| Graph | 确定事实与不确定证据的分层 | Hot / Cold / Frozen |
| **AI** | **API 语义、上下文、最终判断** | **消费 Evidence Bundle** |

**关键词的定位变化**（设计原则 7）：**从「Bug 判定器」变成「候选/事件发现器」。**

词汇表文件头对此有明确自述：

> Keywords here are CANDIDATE GENERATORS, not judges. A hit proposes an event; tree-sitter structure confirms its shape... **Nothing in this file decides that a defect exists.**

**怎么读**：这条纪律解释了为什么词汇表**刻意保守**——`ALLOC` 白名单只列了 C 标准库、Win32、GLib 三族共 20 多个分配器（redis 上只产出 41 个 `ALLOC` 事件）。**列得越多，误报越多**；而「漏掉一个分配器」的代价是召回下降，比「多认一个非分配器」的代价低。**这是一个明确的、有方向性的取舍。**
