## 二、阶段 0：三个阻塞问题

外推表（[01](01-为什么稀疏图.md) §三）不是纸面推演，它直接定义了三个必须先修的架构问题：

| # | 问题 | 300 万行表现 | 性质 |
|---|---|---|---|
| **P1** | 增量更新三张全表 dump | 每次 update **吃 12 GB 内存** | 🔴 致命 |
| **P2** | 多跳 frontier 用 `IN (...)` 绑定 | **frontier > 16,383 直接崩** | 🔴 已复现 |
| **P3** | 单文件 7.8 GB SQLite | 冻存/diff/gitignore 工作流崩 | 🟠 工作流 |

### P2 的根因（一个纯粹的 SQLite 限制）

`get_subgraph` 把 frontier 绑定进 `src_id IN (...)` 和 `dst_id IN (...)`，**同一份列表传两次**。SQLite 上限 32,766 个绑定变量 ÷ 2 ⇒ **frontier 超 16,383 个节点必崩**。

**为什么这对缺陷检测特别致命**：影响面分析恰恰**从 hub 出发**——基类、被广泛 import 的工具模块。**最危险的符号就是最热的符号**，而 hub 的邻居数必然超限。对话场景下这只是「慢」，缺陷场景下是**核心功能不可用**。

**修复**：新增 `id_filter()` 上下文管理器（阈值 900）。小集合照旧按占位符绑定；大集合物化进临时表，查询改为 `IN (SELECT id FROM temp.…)`——**调用方的绑定参数数量不再依赖集合大小**。

**验证（三层）**：

| 层 | 结果 |
|---|---|
| 单元回归（新增 2 项） | ✅ 100/100；**变异验证**：改回原地绑定 → 测试精确复现 `too many SQL variables` |
| 机制两端钉死 | 900 以下走占位符、以上走临时表，两路结果一致 |
| **真实管线复现**（1 hub + 2 万调用者） | 修复前「2 跳 → 崩溃」；修复后 **2 跳 → 20,003 节点 / 40,002 边，1.8 s** |

**怎么读**：这里出现了本项目方法学的一个标志性动作——**变异验证**（mutation verification）。不只是「测试通过」，而是**故意把 bug 改回去，确认测试会精确失败**。这条做法在后续阶段反复出现。

### P1：过读约 1600 倍

| 操作 | 耗时 |
|---|---:|
| `raw_references` 全表载入 | **96.4 ms**（25,040 行）← 最大单项 |
| 实际过滤所需 | **0.06 ms** |

**修复**：三张全表 dump → 定向读取，22.0 MB → 5.9 MB。

### P3 / 阶段 0.4：表达式索引

`layer` 谓词走 `json_extract(metadata, '$.layer')`，无索引时全表扫。

**来源说明（诚实记录）**：4 个索引的 DDL 早已写进 schema，但**从未验证、无测试、无文档**。阶段 0.4 补齐的正是验证与钉子测试，DDL 本身未改。

**实测**（20,003 nodes / 40,002 edges 的真实规模库）：

| 查询 | 带索引 | 无索引 | 加速 |
|---|---:|---:|---:|
| nodes 裸提取 | **0.014 ms** | 18.3 ms | **1300×** |
| edges 裸提取 | 0.014 ms | 20.3 ms | **1470×** |
| `COALESCE != 'knowledge'` COUNT | 0.63 ms | 18.6 ms | 30× |

**测试钉的是查询计划而非 DDL 存在性**——必须出现 `SEARCH … USING INDEX`，`COALESCE !=` 必须走 `USING COVERING INDEX`（证明 metadata 大字段永不被读）。

**踩到并记录的真坑**：`EXPLAIN` 必须用**全新连接**——sqlite3 的语句缓存会让 `DROP INDEX` 后的 EXPLAIN 仍报旧计划。

**怎么读**：**「写进 schema」不等于「已交付」。** 这段记录的价值不在于 1300×，而在于它如实写了「这 4 个索引挂了几周没人验证」。这类诚实记录在本项目里是常态。

### 阶段 0 的一个副产品洞察

当时的存储画像（本仓 26.8 MB）：

| 表 | 体积 | 占比 | 行数 |
|---|---:|---:|---:|
| `raw_references` | 9.31 MB | 57.4% | 25,040 |
| nodes | 5.27 MB | 32.5% | 644 |

而 `raw_references` 里 **80.5% 是 `unresolved`**：

| status | 条数 | 平均 `candidate_symbols` |
|---|---:|---:|
| unresolved | 20,167 | **2 字节**（即 `[]`） |
| resolved | 3,983 | 75 字节 |
| ambiguous | 890 | **349 字节** |

**unresolved 是「稀」的，ambiguous 是「胖」的。**

**怎么读**：设计取舍很清楚——**宁可留下所有解析失败的引用，也不丢证据**。`unresolved` 行虽然数量大，但几乎不占体积；真正占体积的是 `ambiguous`（有多个候选符号，需要全记下来）。**这个分布说明「保留证据」的成本比想象中低。**

## 三、阶段 1–3：矩阵 → 事件 → CFG

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1 | Evidence Matrix：9 大类 38 小类，按**代码操作种类**分类 | ✅ |
| 2 | Semantic Event MVP：事件层落地 | ✅ 四条验收 |
| 3 | Sparse CFG：`CONTROL_REACHES` + 边 flags | ✅ 四条验收 |

**阶段 1 的一个分类学决定**：矩阵按「**代码里的哪种操作出了问题**」切分，**不按 CWE 根因切分**。理由是检测能力来自代码图，按操作分类能让「类别 ↔ 图能力」直接对齐。CWE 编号退化为**参考列**。

**怎么读**：这个决定是有代价的——一个操作类可能引用多个 CWE，一个 CWE 可能被多个操作类引用，部分操作类**没有直接对应的 CWE**。**代价是「对不上 CWE 表」，回报是「每类都能直接映射到一组图特征」。** 这是一个明确的、可质疑的取舍。

## 四、阶段 4：第一个质量基线，以及它推翻了阶段 5

### 阶段 4 交付

`RaceQuery` / `ResourceLifetimeQuery` / `LockOrderQuery` 三个查询 + `DefectEvidenceBundle`。

### 验收②：人工核对 20 条候选

**结果：20/20 全假阳性，precision 0.000。**

| 成因 | 条数 |
|---|---:|
| `ownership` | 10 |
| `identity` | 6 |
| `contract` | 2 |
| `extractor` | 1 |
| `call_argument_loss` | 1 |

**`needs_dfg` = 0 / 20。**

### 这个「0」的含义——本项目最重要的一次发现

**没有任何一条假阳性是「因为缺数据流」造成的。**

候选爆炸（redis 557,315 / llama **1,463,722**，后者是旧码列——见 §五 的口径注意）的主因是**局部变量同名**——一个符号表问题，**不是数据流问题**。抽样的 4 条全是局部变量同名：两个方法各有一个局部 `int n`，就被判成共享 `n`。

**于是原定的阶段 5 被推翻，重拆成四个**：

> 候选生成只需要 AST 里已有的事实（**便宜**），确认需要跨过程推断（**贵一个数量级**）。
> **先修身份，再补访问层，最后才做 DFG；API 契约独立成层，因为它既不是 CFG 也不是 DFG。**

| 阶段 | 内容 | 为什么在这个位置 |
|---|---|---|
| **4.5** | Identity & Extraction Hardening | 最便宜、收益最大；且它是后面每一步的**分母** |
| **5A** | Access Layer | 读/写事实 |
| **5C** | Contract / Ownership | 既不是 CFG 也不是 DFG，独立成层 |
| **5B** | Sparse DFG Core | 最后做——最贵，且前面不修就白做 |

**怎么读**：**这是「可证伪纪律」最有价值的一次兑现。** 原路线图（阶段 5 = 直接做 DFG）在纸面上是合理的。实测一跑，发现假阳性里 DFG 的贡献是 **0/20**，整个优先级排序被推翻。

如果当时按原计划做 DFG，会**先花掉最贵的一步，然后发现它不解决问题**。

## 五、阶段 4.5 / 5A / 5C / 5B：逐层加固

### 阶段 4.5：身份层（收益最大的一步）

| 语料 | 候选削减 |
|---|---:|
| redis-50 | 557,315 → 28,523（**−94.88%**） |
| llama.cpp-69 | 1,463,722 → 58,677（**−95.99%**） |
| **两仓合计** | **2,021,037 → 87,200（−95.69%）** |

**口径注意**：这里的 llama 值是 **1,463,722（旧码列）**，与 §五 末尾五列表里的 **1,398,235** 不同——那是「今日码 + identity=False」列，**今日码复现不出 1,463,722**。redis 两列恰好同值，所以只有 llama 有这个坑。**两个数并存不是笔误**，见 [06](06-实验结果.md) §三 的口径表。

**削减的组成**（这条比总量更重要）：

| 存储类 | libgit2-24 | redis-50 | llama.cpp-69 |
|---|---:|---:|---:|
| `local` / `parameter` / `function_static` | **0 / 0 / 0** | **0 / 0 / 0** | **0 / 0 / 0** |
| 字段 / 文件静态 / 全局 / 未知 | — | 0 / 131 / 153 / 533 = 817 | 285 / 76 / 23 / 1,000 = 1,384 |

**怎么读**：**三个仓上 `local` / `parameter` / `function_static` 的削减都是 0**——也就是说，**这 95% 的削减全部来自「不再把局部变量当成共享变量」这一条**。这不是调参，是**修正了一个概念错误**。

**成本**：

| 语料 | 索引时间 | DB 体积 | 查询时间 |
|---|---|---|---|
| redis-50 | 23.1 → **18.6 s**（−19.5%） | 398 → 412 MB（+3.6%） | 23.6 → 7.8 s |
| llama.cpp-69 | 86.1 → **66.4 s**（−22.9%） | 1.28 → 1.31 GB（+2.1%） | 130.4 → 129.3 s |

**怎么读**：**索引变快了。** 原因是候选少了 ⇒ 后续处理少了。这是一个「修对概念，性能自动变好」的例子。

**一处被证伪的预测**：阶段 4.5 预测 redis 的 `subjects_multi_method` 会在 136–176 之间，**实测 817**。偏差近 5 倍，已如实登记。

### 阶段 5B：Sparse DFG Core + 两条调优 + 参数绑定

**两条前置调优**（纯查询层，冻结库上量，不重建）：

1. **unknown 根成员保留身份**——redis race 264,280 → **10,420**（unknown 桶 261,405 → 7,545）
2. **errno 豁免**——redis **−17,520**，**恰为 `name:errno` 桶的精确值**

**怎么读**：第 2 条的「恰好等于」是一个**强证据**：它证明豁免规则的作用域精确，没有误伤。

**参数绑定（提取侧 + 查询期联结）**：

| 指标 | redis-50 |
|---|---:|
| `calls_seen` | 55,231 |
| `arguments_seen` | 39,905 |
| **`arguments_bound`** | **9,302** |
| `parameter_slot_writes_skipped` | 122,818 |

**穿过写规则（本阶段关键修正，探针自查抓到）**：

只有**穿过参数**的写（成员路径非空如 `p->flags`，或整对象解引用 `*p = v`）才组合进调用方实参根。**裸槽写 `p = x` 是被调方自己名字的重绑定**——C 按值语义下永远摸不到调用方。

**第一稿把它组合进去了，探针抓到 +13,291 条伪候选（127% of 10,420）。** 修后跳过 122,818 条裸槽写。

**怎么读**：这是**工具自己的探针发现了工具自己的错误**。如果没跑这个探针，这个错误会直接进入交付。

**一处被证伪的预测**：参数绑定预测「≪10%」，**实测 redis +38.6%**（+4,019），llama +2.75%。redis 的偏差已如实登记，机制是设计中预期的跨方法 recall 恢复。

## 六、阶段 6：第二批查询，与两个交付级缺陷

### 交付

5 个新查询：`null_flow` / `use_after_free` / `double_free` / `taint_path` / `error_handling`。`QUERY_NAMES` 到 8 个。

### 一次关键的路线裁定

原计划给 `error_handling` 补一个提取侧事实 `result_of`。但实测发现：

- `result_of` 要挂的 `_access_point` 开头即 `if storage not in ACCESS_STORAGES: return None`
- 而 `ACCESS_STORAGES` **不含 `local`** ⇒ 局部变量赋值**不产生 WRITE 点**
- ⇒ `int n = read(fd, buf, len);`（C 里「存调用结果」的主流形态）**永远看不到**

**用户裁定走路线 D**：改用 **CALL 点已有的事实**——CALL 点在赋值右值上时，`subject` 就是**结果落进的那个左值**，且带已解析声明。

**收益**：**零提取改动、零重建。**

| 语料 | `subject_from='assignment'` | 其中 local 且声明已解析 |
|---|---:|---:|
| redis-50 | 14,507 | 12,728 |
| llama.cpp-69 | 87,498 | 81,169 |

**怎么读**：这是一个**「先量清楚再动手」的样本**。原方案要改提取器 + 重建两个库；实测发现已有事实就够了。**省下的是重建时间，保住的是「零提取改动」这条回归面为零的性质。**

### 两个交付级缺陷（都在本阶段发现并修复）

**① `find_paths` 悬崖**

`error_handling` 原经 `_flow_path` → `find_paths(max_hops=4096)`，循环窗口指数爆炸——redis 上 **3,989 个窗口，超过 600 秒 / 13.7 GB 内存不返回**。

修复：`_branch_scan` 记 BFS 前驱，新的 `_route()` 从扫描自己的 BFS 树读出决定点的路线（**零成本、与判决同源**）。

| | 修复前 | 修复后 |
|---|---|---|
| 耗时 | **>600 s（不返回）** | **1.6 s** |
| 内存 | 13.7 GB | — |
| 候选 | — | 与冻结预测**逐位一致** |

**② `max_hops=64` 透传**

交付层默认 `max_hops=64` 透传进窗口判决 ⇒ llama 的 9.1 查询**多出 6,189 条伪候选**（42,739 vs 冻结 36,550）。

修复：`error_handling` 内部**钳到下限 4096**（`_WINDOW_MAX_HOPS`，**可调大不可调小**）+ 钉子测试。

**怎么读**：两个缺陷都不是「算法错」，是**边界条件下的失效**。第一个是复杂度悬崖，第二个是**默认参数在小值上静默产生错误结果**。第二个尤其危险——它不崩溃、不报错，只是答案错了 17%。

### T2 对账闭环（零未归因残差）

验收单初跑有 4 处 failure（两个 population 差 + 连带的求和校验）。逐位归因：

1. **population 是定义拆分**——冻结值 = 已声明子集（14,404 / 85,031）；查询值减去未声明者后**恰好等于冻结值**
2. **backward 是走法形状**——探针在决定点早退、查询走完整层；**同一 population 上两种走法各自逐位复现**

归因后 `verify_t2.py` **PASS**。

**怎么读**：「对不上」有两种可能：**真的错了**，或者**口径不同**。本项目的做法是**先归因到逐位相等**，再宣布通过。**「零未归因残差」是一个比「测试通过」强得多的断言。**

### 阶段 6 的裁定结果

32 条 / 16 层：**TP 1 / FP 31，precision = 1/32 = 0.031**。`needs_dfg` = 2。**零不确定。**

`failure_reason` 分布：契约 10 / 提取器 6 / 其他 5 / 归属 5 / 身份 4 / `missing_read_write` 1。**别名 0，`call_argument_loss` 0。**

**怎么读**：两个「0」值得注意——

- **`call_argument_loss` 从阶段 4 的 1 降到 0**：说明阶段 4.5 的完整 CALL arguments 提取起作用了。
- **`别名` 从阶段 4 的隐含成因降到 0**：说明身份层修好了。

**而 `契约` 上升到 10（主导成因）**：这说明**下一个该修的是契约层，不是数据流层**。**阶段 4 的教训在阶段 6 以另一种形式重现了。**

## 七、方法学：贯穿始终的四条纪律

| 纪律 | 具体做法 | 本知识库中的实例 |
|---|---|---|
| **先冻结预测，再实现** | 探针在冻结库上跑，落盘，两次运行逐位相同 | 阶段 6 的 T1/T2 |
| **对不上就如实报偏差** | 不调规则凑数 | 2 处被证伪的预测（§五） |
| **变异验证** | 故意把 bug 改回去，确认测试精确失败 | 阶段 0.2 |
| **归因到逐位相等** | 「对不上」先分清是错还是口径不同 | 阶段 6 的 T2 闭环 |

**怎么读**：这四条是**可证伪的**——每一条都有本知识库中的具体实例，而不是方法论口号。**这也是本项目最值得被评审的地方：它的数字有出处，它的错误有记录。**
