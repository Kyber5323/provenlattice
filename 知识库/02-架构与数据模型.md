# 02 · 架构与数据模型

> 本篇回答：图长什么样？三层怎么分工？什么进了图、什么故意没进？CFG/DFG 为什么只支持 C/C++？
> 依据：设计文档 §4 / §5 / §12 / §13，以及 2026-09-30 在冻结库上的实测。

## 一、三层图模型

设计文档 §5 把图分成三层。**层与层的分界不是「数据种类」，而是「粒度」**。

```
┌─────────────────────────────────────────────────────────────┐
│ 第三层  Defect Semantic Relations                           │
│   CONTROL_REACHES  ·  DATA_FLOW_TO                          │
│   —— 缺陷推理真正消费的关系                                  │
├─────────────────────────────────────────────────────────────┤
│ 第二层  Semantic Event Layer                                │
│   CALL · DEREFERENCE · READ · BRANCH · RETURN · WRITE ...    │
│   —— 缺陷分析的粒度：不是语句，是「操作」                      │
├─────────────────────────────────────────────────────────────┤
│ 第一层  Structural Code KG                                  │
│   Repository · Directory · File · Symbol(Method/Function/…)  │
│   —— 全局骨架，确定、稳定、不随语义变化                        │
└─────────────────────────────────────────────────────────────┘
```

### 第一层：Structural Code KG（骨架）

稳定代码实体，用 SHA-256 stable identity 寻址。这一层是**跨语言**的——Python 仓和 C++ 仓都有 Repository / Directory / File / Symbol。

**关键设计**：`Method`（及 `Function`）是**骨架节点**，语义事件挂在它下面。这解决了一个基本问题：**没有方法边界，事件就是一盘散沙**——你无法说「这两个访问在同一个方法里」「这两个访问可能并发」。

### 第二层：Semantic Event Layer（粒度）

设计原则 3：**Semantic Event 才是真正的缺陷分析粒度。**

不是「语句」——语句太细，`int x = 1;` 和 `free(p);` 在语法上是同类。事件是**对缺陷有意义的最小操作**。

**已交付的 15 种事件类型**（实测分布，redis-50 阶段 5B 库，共 176,893 个事件）：

| 事件类型 | redis-50 | llama.cpp-69 | 来源 | 语义 |
|---|---:|---:|---|---|
| `CALL` | 55,231 | 208,128 | 词汇表 | 函数/方法调用 |
| `DEREFERENCE` | 44,928 | 116,197 | 结构点 | 解引用 |
| `READ` | 29,137 | 120,382 | 访问点 | 变量读 |
| `BRANCH` | 21,189 | 39,909 | 结构点 | 分支 |
| `RETURN` | 11,900 | 22,011 | 词汇表 | 返回 |
| `WRITE` | 8,406 | 13,317 | 访问点 | 变量写 |
| `CHECK` | 4,304 | 4,464 | 结构点 | 空指针检查 |
| `THROW` | 1,519 | 3,471 | 词汇表 | 非局部退出 |
| `RELEASE` | 77 | 368 | 词汇表 | 释放 |
| `ALLOC` | 41 | 1,792 | 词汇表 | 分配 |
| `LOCK` / `UNLOCK` | 44 / 43 | 255 / 26 | 词汇表 | 加锁/解锁 |
| `THREAD_SPAWN` / `THREAD_JOIN` | 36 / 38 | 318 / 317 | 词汇表 | 线程 |
| `ATOMIC` | 0 | 56 | 词汇表 | 原子操作 |
| **合计** | **176,893** | **531,011** | | |

**怎么读**：三件事。

1. **`ALLOC` / `RELEASE` 是稀有事件**（redis 41 / 77，llama 1,792 / 368）——不是提取器漏了，而是词汇表**刻意保守**：只认白名单里的分配器与释放器。这直接决定了资源类查询的召回上限（见 [07](07-边界与未修缺口.md) §三）。
2. **事件分布本身是语料画像**：redis 的 `CHECK` 密度远高于 llama（4,304 / 176,893 = 2.4% vs 4,464 / 531,011 = 0.8%），而 llama 的 `THROW` 密度是 redis 的 2 倍。**同一套规则在不同语料上的产出结构不同**，这是后面所有 precision 数字不可跨仓外推的原因。
3. **`READ`/`WRITE` 是阶段 5A 才加的**——这就是 README 里 redis 语义点从 139,350（4.5）跳到 171,553（5A）的原因。**语义点是分阶段长出来的，不是一个设计一次到位。**

### 第三层：Defect Semantic Relations（关系）

已交付**三种关系**，都在 `semantic_edges.relation` 里区分：

| 关系 | libgit2-24 | redis-50 | llama.cpp-69 | 含义 |
|---|---:|---:|---:|---|
| `CONTROL_REACHES` | 151,826 | 162,268 | 422,925 | 控制可达（来自稀疏 CFG） |
| `DATA_FLOW_TO` | 5,434 | 6,055 | 11,268 | 数据流（来自稀疏 DFG） |
| `CONSUMES` | 0 | 0 | **2** | 资源消费（实验性，几乎无产出） |
| **控制 / 数据 比** | **28 : 1** | 27 : 1 | 38 : 1 | |

**怎么读**：三件事。

1. **控制边比数据边多约 30 倍。** 这是刻意的：CFG 保留「关键事件之间」的可达关系，而 DFG 只保留五类缺陷相关的 value flow（见 [03](03-稀疏CFG与DFG.md)）。
2. **`CONSUMES` 在三个仓上合计 2 条。** 这是一个**交付了但基本不产出的关系**——它的存在本身就是「先建机制、后看产出」这条路线的一次实测否证。本项目对此的处理是**如实登记，不假装它在工作**（见 [07](07-边界与未修缺口.md) §三）。
3. **数据边的绝对量很小**（5,434 ~ 11,268）。后面所有基于 DFG 的查询（空指针、UAF、双释放）都建立在这个量级上——**这解释了为什么它们天然难以产生大量候选**。

## 二、什么进了图，什么故意没进

这是本项目与 CPG 分歧最大的地方。**下面每一条「没进」都是主动选择，不是没做。**

| 对象 | 状态 | 理由 |
|---|---|---|
| Repository / Directory / File / Symbol | ✅ 进（第一层） | 全局骨架，稳定 |
| 缺陷相关 Event（15 种） | ✅ 进（第二层） | 分析粒度 |
| `CONTROL_REACHES` / `DATA_FLOW_TO` | ✅ 进（第三层） | 推理消费的关系 |
| **完整 AST** | ❌ **不进** | 「AST 临时使用，不永久存储」——解析完即弃 |
| **所有 Identifier / Literal / Expression** | ❌ **不进** | 只有进入词汇表或结构点的才发布为事件 |
| **完整 CFG 中间节点** | ❌ **不进** | 只留关键事件之间的可达关系 |
| **完整 DFG 中间表达式** | ❌ **不进** | 只留五类缺陷相关流 |
| **source text** | ❌ **不进** | 事件只存 source span（行列号） |
| **原始引用** | ⚠️ **进冷层** | `raw_references` 独立表，不参与常规多跳 |
| **别名边** | ❌ **不造边** | `MAY_ALIAS` 只记候选元数据，**绝不创建 `ALIAS` 边** |

**怎么读**：倒数第二行是**本项目最容易被质疑的一条**。AST 不存意味着：任何当时没被识别为「缺陷相关」的语法结构，事后无法从图里补出来——**只能重新解析源码**。这是一个用「可扩展性」换「体积与信噪比」的取舍。设计上的补偿是 `raw_references` 冷层：它保存原始引用证据，可按 `(file_id, start_line)` 精确取回（见 §四）。

最后一行是**证据纪律**：不确定的关系降级为元数据，不升级为边（见 [04](04-缺陷查询与证据包.md) §三）。

## 三、发布管线：一次遍历，两层共用

一条语法事实如何变成图里的一行——这张图是理解「为什么图是自洽的」的关键：

```
源文件
  │
  ├─ 扫描器 scan_repository          ← 决定哪些文件进图（.py/.pyi/.h/.c/.cpp/...）
  │
  ├─ Tree-sitter 解析 → AST           ← 临时，不持久化
  │
  ├─ 事件提取器 extract_hits(root)
  │     └─ 一次匹配，同时喂给两层 ────┐
  │                                   │
  ├─ 声明索引 DeclarationIndex.build  │  ← 读同一棵树，作为「事实」交给 CFG 构建器
  │                                   │
  └─ SparseCfgBuilder.build(root) ────┘
        │
        ▼
   ParsedFile(symbols, references, events, cfg)
        │
        ▼
   build_graph()  ← 发布：事件 → semantic_events，CFG 边 → CONTROL_REACHES
        │                                    DFG 边 → DATA_FLOW_TO
        ▼
   SQLiteStorage.replace_snapshot()
```

**关键点**：`extract_hits` 是**一次匹配**，事件与 CFG 边**来自同一批命中**。源码里对此有明确注释：

> One matcher feeds both layers: the events and the CFG edges come from the same hits, so an operation cannot appear in one and be missing from the other.

**怎么读**：这条设计消灭了一整类 bug——「事件层说有 `free`，CFG 层说没有」这种不一致**结构上不可能发生**。这是本项目在**自洽性**上最有力的一条论证。

**另一条关键点**：CFG 构建器**消费**声明事实，不**生产**它们。声明由独立的 walker 读同一棵树，作为输入交给 CFG。这保证了「身份」在所有层里是同一个——事件、CFG 点、符号节点指向的是同一个 `symbol_id`。

## 四、热 / 冷 / 冻三层存储

设计文档 §12 的分层，对应到 SQLite 的实现：

| 层 | 设计文档名称 | 实现 | 访问模式 |
|---|---|---|---|
| **热** | Semantic Topology | `nodes` / `edges` / `semantic_events` / `semantic_edges` | 常规多跳、typed query |
| **冷** | Evidence | `raw_references` | **不参与常规多跳**，按精确键取 |
| **冻** | Snapshot | `graph_generation` + `shards` + `semantic_fingerprint` | 世代快照与增量判定 |

### 冷层到底怎么用

`raw_references` 保存「解析阶段发现、但尚未被压缩成确定图边的原始引用证据」。它**不参与常规多跳**，只在需要时按 `(file_id, start_line)` 精确取几行。

**实测用例**：阶段 6 的 `taint_path` 查询要判断「这一行的调用是不是 `getenv`」。CALL 事件**不携带被调名**（`matched_name='call_expression'`），被调名只在 `raw_references.raw_name` 里。于是按 `(file_id, start_line)` 联结取回，覆盖率：

| 语料 | 命中 / 总 CALL 点 |
|---|---:|
| redis-50 | 55,209 / 55,231（**99.96%**） |
| llama.cpp-69 | 206,662 / 208,128（**99.30%**） |

**怎么读**：冷层不是「归档」，是**按需取证的索引**。覆盖率不到 100% 的部分（redis 22 条、llama 1,466 条）会走「该行有多个候选 / 无候选 ⇒ 淘汰并计数」的分支——**不猜**。

**另一条纪律**：`target_module` 为空 = 全局函数调用。llama 里 7 条 `system` 被精确分成 2 条空（真 C 调用）与 5 条 `platform`（Python 的 `platform.system()`）。**没有这条规则，taint 查询会把 Python 的调用当成 C 的 sink。**

### 冻层与增量

`semantic_fingerprint` 让增量更新能判断「这个分片的语义是否脏了」。实测增量重建：redis-50 的 5B 库 gen1 → gen2，语义点数与边数**逐位不变**（176,893 / 168,323），耗时 24.7 s → 29.8 s。

**怎么读**：增量**不减少语义层的重建时间**（29.8 s > 24.7 s 是因为它同时做了别的工作），因为语义事实是从源码重新提取的，不走缓存。缓存里**刻意不含 events 与 CFG**——源码注释给出了理由：events 会被存三遍（cache / nodes.metadata / semantic_events），而 `semantic_events` 是唯一被读的副本；且文件变了本来就要重新提取，缓存买不到任何东西。

## 五、语义层的语言边界（重要）

**边界不在「事件」，在「CFG/DFG」。** 这一条容易说错，必须精确。

| 语言 | 解析器 | 事件 | CFG | DFG | 8 个查询 |
|---|---|---|---|---|---|
| C / C++ | `CppTreeSitterParser` | ✅ | ✅ | ✅ | ✅ |
| Python | `TreeSitterParser` | ✅ | ❌ | ❌ | ❌ |

**根因**：整个代码库里，**唯一构造 CFG 的地方是 C++ 解析器**（`parsing/cpp.py:100-102` 调用 `SparseCfgBuilder`）。事件提取则是**两条路径共用的**——`parsing/events.py` 的 `EventExtractor` 同时被 `cpp.py:13` 与 `python.py:10` 导入。所以 Python **有事件，没有 CFG/DFG**。

**实测确认**（本仓 Python 自索引，`mirror-fresh.db`）：`semantic_events` 共 12,583 行——

| 来源 | 文件数 | 事件数 |
|---|---:|---:|
| **Python 源文件** | 93 | **12,508** |
| C/C++ 测试夹具 | 10 | 75 |

事件类型分布是 `CALL 11,178 / RETURN 1,138 / THROW 95 / ...`，**一个 `DEREFERENCE`、一个 `WRITE` 都没有**——因为这两类来自 CFG 点，而 CFG 只有 C++ 路径会建。

**怎么读**：这条边界必须主动说，否则评审会以为「支持所有语言」。

- 对 **C/C++ 仓**：语义层完整可用（本知识库所有真实仓数字都来自 C/C++ 仓）。
- 对 **Python 仓**：有**事件层**（CALL / RETURN / THROW 等，来自共享的 `EventExtractor`），**没有 CFG/DFG**，因此**没有 WRITE / DEREFERENCE 点，8 个缺陷查询全部不适用**。

**别把这条说成「Python 什么语义都没有」**——它有事件；缺的是事件之间的控制流与数据流关系，而 8 个查询全部建立在这些关系上。

扩展路径是清晰的——`parser_for_language` 是一个工厂函数，为 Python 补一个 `SparseCfgBuilder` 等价的实现即可——**但这是未做的工作，不是已做的**。

## 六、确定性：SHA-256 stable identity 的代价与回报

设计原则 12：**持久化继续保留 SHA-256 stable identity。**

**回报（实测）**：同一输入两次索引，**两张语义表在排除 `generation` 列后字节完全一致**。

**代价**：完整 `.db` 文件**不是**字节可复现的——实测 412,614,656 → 413,036,544 字节（相差 0.1%）。差异来自页分配顺序等 SQLite 内部行为，**不影响语义内容**。

**怎么读**：这是本项目「确定性」承诺的**精确边界**，必须说准：

- ✅ **语义内容确定**：同样的输入，同样的事件、同样的边、同样的 ID。
- ❌ **文件字节不确定**：`.db` 的二进制不是逐字节可复现的。

如果评审问「你们说确定性，那我两次跑出来的库文件为什么不一样大」——答案是上面这条边界，而不是含糊其辞。

**另一处相关取舍**：SHA-256 ID 带来体积（见 [01](01-为什么稀疏图.md) §三 问题 1）与遍历开销，而设计原则 11 的 integer ID + CSR **尚未交付**。这是一个**主动选择的、尚未偿还的技术债**。
