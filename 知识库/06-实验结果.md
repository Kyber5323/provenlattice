## 二、语义层的代价：libgit2-24 双构建 A/B

同一个仓（`libgit2-24`），同一个数据库里的两代构建，`graph_generation` 表里两次都记着 `mode: full`：

| | gen1 | gen2 |
|---|---|---|
| `created_at` | 2026-09-29 07:59:30 | 2026-09-29 08:04:45 |
| `files_scanned` | 1,034 | 1,034 |
| 语义层 | **不存在**（V0.3 无 `sparsecfg.py`） | 存在 |

**这是本项目最干净的一组对照**——两次构建相隔 5 分钟、同一台机、同一个仓、同样的 1,034 个文件，**唯一的变量是 ProvenLattice 的代码版本**（`5ef47d9` V0.3 → `13e797b` 阶段 4–6）。

| 指标 | gen1（无语义层） | gen2（有语义层） | Δ |
|---|---:|---:|---:|
| `files_scanned` | 1,034 | 1,034 | 0 |
| `raw_references` | 88,220 | 89,438 | +1.4% |
| **`nodes_created`** | **34,801** | **14,452** | **−58.5%** |
| `edges_created` | 64,514 | 44,614 | −30.8% |
| `semantic_points` | — | 182,227 | — |
| `semantic_edges` | — | 157,260 | — |
| `index_time_ms` | 12,628.6 | 32,075.2 | **+154%** |
| `database_size` | 207,491,072 B | 508,362,752 B | **+145%** |

### 那 −58.5% 是什么？——完整归因

节点数**下降**了 20,349，这不是笔误，也不是去重。**归因过程**：

1. 读两代代码的 `parsing/cpp.py`，发现 `_function()` 在两代之间多了一个检查：
   ```python
   if node.type != "function_definition":
       if self._find_function_declarator(declarator) is None:
           return False          # ← 旧码没有这三行
   ```
   旧码会把**变量声明**（`int x = 1;`、`git_repository *repo;`）也当成函数声明，造出名为 `f.x` 的幻影 `Function` 符号。

2. **直接实验**：在 libgit2-24 上分别用新旧两套 `_function` 解析全部 1,034 个文件，数符号：

   | 提取器 | 符号数 |
   |---|---:|
   | 旧行为（无 declarator 检查） | **33,667** |
   | 新行为 | **13,318** |
   | 差 | **20,349** |

3. **算术闭合**：

   | | 符号 | + 文件 | + 目录 | + 仓 | = 节点 |
   |---|---:|---:|---:|---:|---:|
   | gen1 | 33,667 | 1,034 | 99 | 1 | **34,801** ✓ |
   | gen2 | 13,318 | 1,034 | 99 | 1 | **14,452** ✓ |

**归因结论：20,349 的差额 100% 来自这一处 declarator 检查。**

**怎么读**：这是一个**「看起来是优化，实际是修 bug」**的典型案例。单看 A/B 表，会以为「新版节点少了 58%，是去重做得好」——**完全不是**。真相是**旧版凭空造了 20,349 个不存在的符号**。libgit2 是头文件密集型 C 库，每个结构体成员、每个全局变量声明都会中招。

**没有归因，这张 A/B 表会被读成完全相反的意思。** 这也是本知识库坚持每个数字配「怎么读」的原因。

### 代价的两个口径：合计值与语义层自身

**这一组 A/B 变的是「代码版本」（V0.3 → 阶段 4–6），一次动了三件事**：加语义层、修 declarator、加稀疏 CFG/DFG。所以时间与体积的差值**不是语义层单独的账**：

| 口径 | 索引时间 | 库体积 | 怎么来的 |
|---|---:|---:|---|
| **合计**（实测，两代之差） | 12.6 s → 32.1 s（**+154%**） | 198 MB → 485 MB（**+145%**） | 两个数都从 `graph_generation` 读出 |
| **语义层自身** | **≥ +154%** | **≥ +145%** | 见下 |

**为什么自身成本是「≥」而不是等号**：declarator 修复**删掉了 20,349 个幻影节点**（§二上），删节点是**减成本**的。也就是说，gen2 是在「比 gen1 少 20,349 个符号」的前提下，仍然比 gen1 多花了 154% 的时间和 145% 的体积。**把这份减量加回去，语义层自身只会更贵。**

**怎么读**：**这是一个下界，不是一个点估计。** 用在容量规划里是安全的——真实代价只会更高，不会更低。至于值不值——取决于查询层的产出，见 §四。

**登记**：本项目**没有**单独测过「只有语义层、没有 declarator 修复」的那一代，所以**无法给出语义层成本的精确值**，只能给这个下界。要精确值需要再造一代构建，未做。

## 三、候选削减：五列对比

同一个查询（`race_condition`，矩阵 1.1），逐层加固：

| 层 | redis-50 | llama.cpp-69 |
|---|---:|---:|
| C1 基线（阶段 4） | 557,315 | 1,398,235 |
| C2 + 身份（阶段 4.5） | 28,523 | 58,677 |
| C3 + 读/写（阶段 5A/5C） | 264,280 | 137,899 |
| C4 + 未知根身份 + errno 豁免（5B） | 10,420 | 98,448 |
| C5 + 参数绑定（5B） | **14,439** | **101,159** |
| **C1 → C5** | **−97.4%** | **−92.8%** |

**先说一个必须知道的口径陷阱：llama 的 C1 有两个值。**

| C1 口径 | redis-50 | llama.cpp-69 | 说明 |
|---|---:|---:|---|
| **本表所用**（identity=False，**今日码**） | 557,315 | **1,398,235** | 逐位复现 R-13 的 **C3 拼写列** |
| 阶段 4.5 自己那张表（**旧码**） | 557,315 | **1,463,722** | R-13 的 C1/C2 列，**今日码复现不出** |

**redis 两处恰好同值，所以只有 llama 有这个坑。** 看到 1,463,722 与 1,398,235 并存**不是笔误**，是两列不同代的测量。**本知识库的五列表一律用 1,398,235**（它是今日码可复现的那个）。

**控制条件（这张表可信的前提）**：

- **C2 在 C1 携带的每一个键上逐位复现 C1**（`control_report()` **逐键比对，不是抽样**）。所以 C3/C4 与 C1 的差读作**改动的效果**，而不是仪器的漂移。**注意**：这条控制是在**旧码列**（llama 1,463,722）上做的，其 `candidates_returned` 为 redis 557,372 / llama 1,000,743。
- C1 的 `candidates_returned` 与各查询自报之和**完全相等**（redis 557,315 + 2 + 55 = 557,372）。llama 的 **463,722** 差额**全部**来自 `race_condition` 的 1M `population_capped` 截断（1,463,722 − 1,000,000），**不是去重**——这个差额数字属于**旧码列**，与表中 1,398,235 不是同一次测量。

**怎么读**：三条。

1. **C2 → C3 是上升的**（28,523 → 264,280）。这是阶段 5A 引入读/写区分时「未知根塌陷」的**登记成本**，阶段 5B 就是来修它的。**这条上升曲线是设计的一部分，不是回归。**
2. **C2 / C3 两列是冻结工件引用**，不是今日代码重测——`identity_probe.json` 的裁断臂。**今日代码在旧库上跑不出这两个值**（登记在案）。
3. **削减的组成比总量更重要**：`local` / `parameter` / `function_static` 三类在两仓上的削减都是 **0**。**95% 的削减全部来自「不再把局部变量当共享变量」这一条概念修正。**

5. **`error_handling` 是最大的产出**（redis 4,084 / llama 32,466），机制清楚：population 是 `stored-call-result`（redis 14,507 / llama 87,498），扫描后判 `unchecked`。**判据最宽，产出最大，精度也最需要人工看。**
6. **三态分布本身也是跨仓差异的**：`null_flow` 在 libgit2/redis 上 `resolved` 只占 20%/18%，在 llama 上却是 **84%**（497/591）。**同一个查询的「确定程度」随语料变化**——不能拿一个仓的三态比例去描述另一个仓。

### 慢的那个查询随语料而变

redis-50 与 llama.cpp-69 在**同一批运行**中的耗时（两列可比，但与上表不是同一批）：

| 查询 | redis-50 | llama.cpp-69 |
|---|---:|---:|
| `use_after_free` | **303.5 s** | 15.8 s |
| `double_free` | 116.3 s | 23.7 s |
| `resource_lifetime` | 7.6 s | **139.1 s** |
| `race_condition` | 8.0 s | 55.0 s |
| `null_flow` | 4.8 s | 46.1 s |
| `error_handling` | 5.3 s | 19.0 s |
| `taint_path` | 5.1 s | 15.3 s |
| `lock_order` | 4.8 s | 14.3 s |

**怎么读**：三件事。

1. **同一个查询在不同仓上可以差二十余倍**（两个**低噪声**测量：`use_after_free` redis 124.5 s vs libgit2 5.1 s，**24 倍**；同一批内 `resource_lifetime` llama 139.1 s vs redis 7.6 s，**18 倍**）。主导项是 `find_paths` 的路径枚举，**路径数取决于该仓的循环结构密度**。**任何性能承诺都必须绑定语料**，不能给一个「平均查询时间」。
2. **「最慢的查询」不是固定的**：redis 上最慢的是 `use_after_free`（303.5 s），llama 上最慢的是 `resource_lifetime`（139.1 s），libgit2 上八查询全在 **7.6 s 以内**。**「哪个查询慢」是语料的属性，不是查询的属性。**
3. **⚠️ 耗时不可复现，候选数可复现。** 上表这 8+8 个耗时是在**同时跑着别的库查询**的机器上测的，因此比上表（受控测量）高约 2 倍。**候选数在同一批里与冻结记录逐位相同**——**确定性保证的是语义内容，不是墙上时间**。引用耗时必须写清测试条件。

**`uncertain` 不进 precision 比值**，但在表内可见；**空层报 `n/a` 而不是 `0.0`**。

## 八、两个交付级缺陷（阶段 6 发现并修复）

### ① `find_paths` 悬崖

| | 修复前 | 修复后 |
|---|---|---|
| 耗时 | **>600 s（不返回）** | **1.6 s** |
| 内存 | **13.7 GB** | — |
| 触发条件 | redis 的 3,989 个循环窗口 | — |
| 候选 | — | 与冻结预测**逐位一致** |

**根因**：`find_paths` 是**路径枚举器**（每个队列项自带 visited 集），用它做不可达判定会指数爆炸。**修复方式不是加缓存，是换工具**——从分支扫描自己的 BFS 树里读出路线（零额外成本、与判决同源）。

### ② `max_hops=64` 透传

| | 修复前 | 修复后 |
|---|---|---|
| llama 9.1 候选 | **42,739** | **36,550**（= 冻结值） |
| 伪候选 | **+6,189（+17%）** | 0 |

**根因**：交付层默认 `max_hops=64` 透传进窗口判决。**64 太小**——实测会造出 12 条假「不可达」。

**修复**：内部钳到下限 4096（`_WINDOW_MAX_HOPS`，**可调大不可调小**）+ 钉子测试。

**怎么读**：两个缺陷性质不同，第二个更危险。

- ① 是**复杂度悬崖**：会挂，会 OOM，**看得见**。
- ② 是**静默错误**：不崩溃、不报错，**答案错了 17%**。如果不是冻结预测做对拍，它会被当成正常结果交付。

**这就是「先冻结预测」这条纪律的直接回报。**

## 九、两处被实测证伪的预测

| 阶段 | 预测 | 实测 | 偏差 |
|---|---|---:|---:|
| 4.5 | redis `subjects_multi_method` 136–176 | **817** | ~5× |
| 5B | 参数绑定增量「≪10%」 | redis **+38.6%**（+4,019） | 远超预测 |

**怎么读**：两处都**如实登记，没有调规则凑数**。

- 4.5 的偏差说明「多方法共享主体」在 redis 上比预期普遍得多。
- 5B 的偏差有明确机制——设计中预期的跨方法 recall 恢复，且**增量全部是 `ambiguous`**（零升级），抽样确认是真实 redis 并发习语。llama 同项 +2.75%，**在预测内**。

**第二处的价值**：它说明**同一个改动在不同语料上可以差 14 倍**（38.6% vs 2.75%）。这是「单仓结论不可外推」的又一个实例。
