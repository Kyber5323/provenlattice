# 07 · 边界与未修缺口

> **如果只读一篇，读这篇。**
> 本篇回答：这个系统**不能**做什么？哪些是设计选择、哪些是未做的工作？
> 依据：`AGENTS.md` 各阶段「登记」条目、`defect_matrix()` 实测、源码中的自述注释。

---

## 一、最重要的一条：它不确认缺陷

**实测**（`defect_matrix()`，无需开库）：

> **`coverable_now` 为 `True` 的模式：0 / 13。**

13 个已登记的模式，**全部**回答「现在不能被确认」。

| | 数量 |
|---|---:|
| `coverable_now` = True | **0 / 13** |
| `candidate_coverable_now` = True | 9 / 13 |
| 两者皆 False（未展开） | 4 / 13 |

**怎么读**：这不是「还没做好」，是**设计的一部分**。源码注释写得很直接：

> 1.1 answering "no" and "yes" at once is the point, not a contradiction.

**正确的描述是：**

> ProvenLattice 是**缺陷候选生成器 + 证据包构造器**，**不是缺陷检测器**。
> 它把「在 69 万行里找值得看的 100 个地方」从不可做变成可做；
> 把「这些地方到底有没有 bug」留给 AI 与人工。

**如果答辩时被问「你们的准确率是多少」，正确的回答不是报 precision，而是先纠正这个定位。** 报 3.1% 会被理解成「检测器很差」；实际是「候选生成器的 32 条抽样里 1 条为真，其余 31 条是它明确标注为『待确认』的候选」。

**每一条候选都带 `missing_evidence`**，明写「我缺什么才能确认」。这是它敢说「不能确认」的机制保障。

## 二、语言边界：CFG/DFG 只有 C/C++

**边界不在事件，在 CFG/DFG。** 这一条要说准，说错会被追问。

| 语言 | 结构层 | 事件 | CFG | DFG | 8 个查询 |
|---|:---:|:---:|:---:|:---:|:---:|
| C / C++ | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Python** | ✅ | **✅** | ❌ | ❌ | ❌ |

**根因**：全代码库中**唯一构造 CFG 的地方是 C++ 解析器**（`parsing/cpp.py:100-102`）。Python 路径不进这一步。但**事件提取是两条路径共用的**——`parsing/events.py` 的 `EventExtractor` 同时被 `cpp.py` 与 `python.py` 导入。

**实测确认**（本仓 Python 自索引）：12,583 个语义事件里，**12,508 个来自 93 个 Python 文件**，只有 75 个来自 10 个 C/C++ 测试夹具——一个 `DEREFERENCE`、一个 `WRITE` 都没有，因为这两类来自 CFG 点。

**怎么读**：**这是一个必须主动说的边界。** 不主动说，评审会以为「支持所有语言」，然后在 Python 仓上试，发现**事件表是满的、查询结果却是空的**——那比全空更难解释。

**准确的表述**：**Python 有事件层，没有事件之间的控制流与数据流关系；8 个查询全部建立在这些关系上。**

**扩展路径是清楚的**（`parser_for_language` 是工厂函数，为 Python 补一个等价的 CFG 构建器即可），**但这是未做的工作，不是已做的**。

## 三、覆盖边界：矩阵 38 类，展开 9 类

| | 数量 | 占比 |
|---|---:|---:|
| 缺陷证据矩阵总类数 | **38** | 100% |
| `defect_patterns.toml` 登记的模式 | 13 | 34% |
| 有查询绑定的模式 | **9** | **24%** |
| 已交付的查询 | 8 | — |

**未登记的 25 类不是「待办」，是「未覆盖」**——按「缺陷反向决定 Schema」的设计，**没展开的缺陷族在图里没有对应结构**。

### 四个未展开模式的理由

| 模式 | 未展开理由 |
|---|---|
| 4.5 句柄/资源泄漏与关闭不足 | OPEN/CLOSE 词表冲突（两文档冲突，已登记） |
| 9.2 返回值未传播 | 需 AI 侧 API 语义 |
| 9.3 缺少错误传播 | **需跨方法传播——图无跨方法控制边** |
| 9.4 异常未捕获 / 异常安全 | 需 catch 建模 |

**怎么读**：9.3 的理由是一条**结构性限制**，不只是「没做」：**本项目没有跨方法的控制流边**。`CONTROL_REACHES` 是方法内的。任何需要「跨函数追踪控制路径」的缺陷族，在当前架构下都做不了。

### 一处文档不一致

设计文档 §9 写「**36 类**」，矩阵文档标题写「**9 大类 38 小类**」。**本知识库以 38 为准，这个不一致尚未对齐。**

## 四、判据边界：DFG 的四种不产边形态

| # | 形态 | 为什么不产边 |
|---|---|---|
| 1 | `free(p); sink(p)` | `CALL` 不在 `USE_EVENTS` 里 |
| 2 | `free(p); p = NULL; *p` | 落进 `null_to_deref` 而非 `free_to_use` |
| 3 | `p = 0` / `p == 0` | `null_node_types` 只认字面量 `null`（继承登记，未翻案） |
| 4 | `free(p); free(q)`（q 别名 p） | 没有 release→release 关系 |

**第 1 条在查询层有部分补偿**（`use_after_free` 查询期组合 CALL 作为 USE），但：

- DFG **本身仍然不铸这条边**
- 这类候选**恒为 `ambiguous`**——`_root_identifier` 剥掉 `&`，`f(p)` 与 `f(&p)` 在图上不可区分
- 且**实测这是主体不是边角**：redis 的 581 条 UAF 候选中几乎全部来自「出参重分配」形态

**第 3 条的后果**：`p == 0` 与 `p == NULL` 在语义上相同，但只有后者被识别。**这是一个纯漏报源，且无法通过调参修复**——需要扩展 `null_node_types`。

## 五、已知残量清单

下面每一条都是**已知的、被记录的、未修复的**缺口。

### 5.1 局部变量不产生 WRITE 点

`ACCESS_STORAGES` **不含 `local`**（源码有逐项说明为什么含其余六类）。

**后果**：局部变量赋值不产生 WRITE 点 ⇒

| 盲区 | 表现 |
|---|---|
| `uaf_local_nulled` | 局部 `p = NULL` 后**仍报**候选（杀不掉活跃的释放身份） |
| `df_local_nulled` | 局部置空后**仍报 `resolved`**（造不出中间 def） |

**参数版本的两个形态都正确淘汰**（`CALL_INTERVENING_DEF` / `INTERVENING_DEF`）——**只有局部变量版本错**。

**两个形态已被钉在测试里**（`Stage6QueryTests`），是阶段 6 的**已知残量**。

**怎么读**：这是**「保守选择的副作用」**。把 `local` 加进 `ACCESS_STORAGES` 会让读/写点全面重铸、既有查询的零移动闸失去参照——**代价等同一次独立阶段**。当时的判断是「不改」，理由留档。

### 5.2 别名：两侧都无事件的对仍然丢失

`q = p; free(p); sink(q)` 这类靠别名传播的缺陷：

- **一侧有事件** ⇒ 靠 alias 闭包**部分恢复**
- **两侧皆无事件** ⇒ **发布不出任何东西**

这是设计原则 9（不确定关系不进 Hot Graph）的**直接代价**：`MAY_ALIAS` 只记候选元数据，**绝不创建 `ALIAS` 边**。

**怎么读**：**这是一次主动选择的漏报。** 换的是「不会把猜测当事实」。**答辩时应主动说明这是一个 trade-off，而不是缺陷。**

### 5.3 循环变量 / lambda 捕获无作用域身份

`subject_storage='unknown'` 且无 `subject_decl`。

**后果**：llama.cpp 上 `double_free` 的候选 **99% 是 `unresolved`**，且集中在**少数站点**——18 个连续 range-for 的 `delete e;`，以及 lambda 捕获 `[buf=_buf]{std::free(buf);}`。

**怎么读**：**这不是「99% 的代码有问题」，是「少数几个站点被反复报告」。** 数字必须配这个解释才有意义。

**for-init / range-for 声明的身份是一个具体的 5B 缺口**，登记为路线图项。

### 5.4 `arguments` 被压紧

`_call_arguments` 结尾会过滤掉没有根的实参 ⇒ **实参下标不是位次**。

**后果**：`taint_path` 的位次判据被限制为「`arity` 可证的形态」；`snprintf` **因此被撤下**（它的危险位是 2，压紧后与「字面量格式串被丢后的首个变参」不可区分，会假命中）。

**怎么读**：这是一个**因为工具自身限制而主动缩小检测范围**的例子。**一个带位次的实参事实会解除这个限制**——登记为路线图项。

### 5.5 次序敏感窗口

同层 use 先于分支决定的窗口：**redis 2 / llama 26**。两种实现一致判 `unchecked`。**登记，不改。**

### 5.6 其他继承登记（未翻案）

| 项 | 状态 |
|---|---|
| 短路条件不展开（`p != NULL \|\| p->f` 漏报） | 继承登记 |
| 括号解引用 `(*p) = v` 不组合 | 登记 |
| C++ 引用参数的裸写是真穿过写，本规则**保守拒绝** | 登记 |
| `_WINDOW_MAX_HOPS` 可调大不可调小 | 设计约束 |

## 六、未修的性能与架构项

| 项 | 现状 | 影响 |
|---|---|---|
| **`find_paths` 枚举是瓶颈** | redis：`use_after_free` 124.5 s / `double_free` 64.8 s；llama：`resource_lifetime` 139.1 s | 修复方案**已知但未实施** |
| **integer ID + CSR 未交付** | 原则 11 未做 | 语义层占体积 **64–72%** |
| **Local Deep Analysis 未做** | 原则 15 未做 | 复杂问题只能靠全局稀疏图 |
| 阶段 7（冷热拆分 + 分析副本） | **未启动** | 单文件 7.8 GB 的 P3 问题仍在 |
| `raw_references` 从主库剥离 | 未做 | 主库 7.8 GB → ~2 GB 的优化未落地 |
| `$.scope` 表达式索引 | 未做（实测每次全表扫 21 ms） | 线性外推到百万行 ~0.5 s/update |

**怎么读**：**这是一份真实的技术债清单，不是「未来工作展望」。** 每一项都有实测支撑的代价，且都在路线图上。

**最该被追问的是第一项**：`use_after_free` 在 redis 上要 124.5 秒、`resource_lifetime` 在 llama 上要 139.1 秒——**对一个交互式查询工具来说这是不可接受的**。修复方案已知（换掉 `find_paths` 的枚举），**但未实施**。

**注意瓶颈的位置随语料移动**：redis 上最慢的是 `use_after_free`，llama 上最慢的是 `resource_lifetime`，libgit2 上八查询全在 **7.6 s 以内**。**「哪个查询慢」是语料的属性**——所以这个缺口不能靠「优化某个查询」关掉，只能靠换掉共用的枚举器。

## 七、工具自身的错误记录

**这一节存在的意义：证明「如实登记」不是口号。**

### 探针自身的教训（三次）

| # | 错误 | 后果 | 如何发现 |
|---|---|---|---|
| 1 | `is_target=lambda info: info.get("point_id", dst) == dst` | **恒真**——把「源有出边」误读成「可达」 | 探针第一版自查 |
| 2 | `Reach` 记忆化对象在循环内重建 | 性能崩坏 | 探针自查 |
| 3 | 别名闭包按 owner 全表扫 | llama 上 **4 亿次迭代，120 s 不返回** | 探针自查 |

**第 1 条的成因值得记录**：`materialize_points` 的记录里**没有 `point_id` 键**，所以 `.get("point_id", dst)` 永远返回默认值 `dst`。**正确惯例是身份比较 `info is points[dst]`。** 这条写进了探针的 docstring。

### 一个「写进 schema 但从未验证」的教训

阶段 0.4 发现：4 个表达式索引的 DDL **早已写进 schema**，但**从未验证、无测试、无文档**，挂了几周没人发现。

**怎么读**：**「写进代码」不等于「已交付」。** 这个教训直接催生了后续的钉子测试惯例——钉的是**查询计划**而非 DDL 存在性。

### 一处测量时的真坑

`EXPLAIN` 必须用**全新连接**——sqlite3 的语句缓存会让 `DROP INDEX` 后的 EXPLAIN **仍报旧计划**。这会让性能测试**静默地测出错误结论**。

## 八、一张「能说 / 不能说」对照表

答辩时最容易说错的几句话：

| ❌ 不能说 | ✅ 应该说 |
|---|---|
| 「precision 3.1%」 | 「32 条抽样中 1 条为真；样本按仓库×缺陷键×状态分层，每层 1–2 条，**分层精度无统计意义**」 |
| 「能检测空指针 / UAF / 双释放」 | 「能生成这三类的**候选**并附证据包；`coverable_now` 全为 False，**不能确认**」 |
| 「支持所有语言」 | 「结构层跨语言；**CFG/DFG 与 8 个查询只支持 C/C++**」 |
| 「覆盖 38 类缺陷」 | 「矩阵定义 38 类，**登记 13 类，展开 9 类**」 |
| 「确定性，两次跑结果一样」 | 「**语义内容**确定（语义表字节一致）；**库文件字节不确定**（差约 0.1%）」 |
| 「用了完整 CPG」 | 「**刻意不做完整 CPG**，只做缺陷导向的稀疏图」 |
| 「候选减少 97.4% 是因为数据流」 | 「**95% 的削减来自身份层**——不再把局部变量当共享变量；`needs_dfg` 在阶段 4 是 **0/20**」 |
| 「用了 CSR / 整数 ID」 | 「**未交付**（原则 11）；当前是 SHA-256 ID + 普通索引，语义层占体积 64–72%」 |
| 「异常路径已建模」 | 「`exception` 边在 C++ 仓有 1,182 条，**两个 C 仓为 0**；9.3/9.4 未展开」 |
| 「测试很全」 | 「296 / 296；覆盖率口径：**9/38 模式有查询**」 |

## 九、这张清单本身的意义

上面所有条目，**没有一条是评审发现后补记的**。它们分布在：

- `AGENTS.md` 各阶段的「登记」段
- `defect_patterns.toml` 的文件头注释
- 源码里的 docstring 与注释
- 测试里的钉子（把已知残量钉住，防止被误当成已修）

**怎么读**：这是本项目**最值得被评审的地方**——不是「做得有多好」，而是**它对自己的边界知道得多清楚**。

一个工具知道自己不能做什么，才能被安全地使用。**一个声称什么都能做的工具，无法被信任。**
