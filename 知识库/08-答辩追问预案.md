# 08 · 答辩追问预案

> 预判 15 个问题与回答要点。每条都指向本知识库中的证据位置。
> **原则：先纠正问题的前提，再给数字。** 大多数尖锐问题源于一个错误的前提。

---

## Q1 · 为什么不做完整 CPG？CPG 是学术界的主流做法。

**先纠正前提**：不是「做不到」，是**目标不同**。

| | CPG | 本项目 |
|---|---|---|
| 目标 | 程序语义的**完整表示** | 缺陷证据的**密度** |
| Schema 由什么决定 | 语法产生式 | **缺陷清单** |

**三条实测依据**：

1. **空间**：完整 CPG 会把每个 statement / expression / literal 都变成节点。本项目即使只保留缺陷相关的部分，语义层仍占体积 **64.3%**（libgit2-24）。
2. **AI 不需要**：`taint_path` 在 libgit2 上有 2,988 条 `input_to_sink` population，**按判据筛完一条不剩**。**稀缺的不是事实，是判据**——塞进更多语法细节不会多出一条真候选。
3. **噪声**：从单个函数出发 **6 跳覆盖全部 14,452 个节点**（3 跳 68.6%）。无差别扩展在任何真实仓上都退化成「把整个图交给模型」。

**主动说出代价**：**「缺陷驱动」意味着没写的缺陷就没有对应的图**——38 类矩阵只展开 9 类。**这是这个选择的必然结果，不是执行力问题。**

→ [01](01-为什么稀疏图.md) §三、§四

## Q2 · precision 只有 3.1%，这东西有什么用？

**先纠正前提**：**这个数字不是「检测器的准确率」，是「候选生成器的抽样命中率」。**

**三条口径必须一起说**：

1. **32 条样本分 16 层，每层 1–2 条** ⇒ **分层精度没有统计意义，只有合计有意义**。项目文档明写「不能说 precision = 0%」。
2. **`coverable_now` 全 13 个模式都是 False**——**工具自己声明不能确认**。它不是检测器。
3. **31 条假阳性不是「错了」，是「待确认的候选」**，每条都带 `missing_evidence`，明写「缺什么才能确认」。

**真正的价值主张**：

> 把「在 69 万行里找值得看的 100 个地方」从不可做变成可做；
> 把「这些地方到底有没有 bug」留给 AI 与人工。

**主动说出进展**：阶段 4 → 阶段 6，`alias` 从隐含成因降到 **0**、`call_argument_loss` 从 1 降到 **0**——**阶段 4.5 的身份层投入有实测回报**。

→ [04](04-缺陷查询与证据包.md) §五、[06](06-实验结果.md) §六

## Q3 · 你怎么证明这个图是「对」的？

**四层证据**：

| 层 | 证据 |
|---|---|
| **自洽性** | 事件与 CFG 边**来自同一批命中**（一次匹配喂两层）⇒「事件层说有 `free`，CFG 层说没有」**结构上不可能** |
| **确定性** | 八查询二次运行证据 ID 逐位相同；**两张语义表字节完全一致** |
| **对拍** | 每个阶段的冻结预测 vs 实现，**零未归因残差** |
| **人工裁定** | 两个质量基线（20 条 / 32 条），逐条裁定并记录 `failure_reason` |

**主动说出边界**：**没有做完整的人工金标保真度评估**——现有的是**候选级**人工裁定，不是**图级**保真度度量。`experiments/fidelity_v1/` 有相关计划，但依赖仓外数据库。

## Q4 · 一个函数 6 跳就覆盖全图，那你的「稀疏」有什么意义？

**这是最好的问题，因为它指向了设计的核心。**

**稀疏的意义不在于「图更小」，在于「查询有判据」。**

对比：

| | 无差别 N-hop | Typed Query |
|---|---|---|
| 输出 | 子图（14,452 个节点） | 候选 + 三态 + 证据路径 + **缺失证据** |
| 淘汰 | **无** | **显式计数**（`GUARDED` 14 / `PATH_DISJOINT` 2 …） |

**具体到数字**：`race_condition` 在 libgit2 上，`subjects_considered` 是 **133,648**，`read_read_pairs` 是 **923,444**，最终候选 **11,089**。**这个收敛不是靠跳数限制，是靠判据。**

**另一个关键点**：`CONTROL_REACHES` **不是传递闭包**——A→B 与 B→C 都存在时 A→C 可能不存在。所以它不会像无差别 BFS 那样自动饱和。

→ [03](03-稀疏CFG与DFG.md) §一、[04](04-缺陷查询与证据包.md) §一

## Q5 · 为什么只有 C/C++？Python 呢？

**直接承认，但要说准**：**Python 有事件层，没有 CFG/DFG 层。**

| 语言 | 结构层 | 事件 | CFG/DFG | 8 个查询 |
|---|:---:|:---:|:---:|:---:|
| C/C++ | ✅ | ✅ | ✅ | ✅ |
| Python | ✅ | **✅** | ❌ | ❌ |

**为什么这一栏要精确**：说「Python 什么都没有」是错的，而且**一测就露**——对本仓（Python）自索引，`semantic_events` 有 **12,583 行，其中 12,508 行来自 93 个 Python 文件**。事件表是满的。

**根因**：全代码库中**唯一构造 CFG 的地方是 C++ 解析器**（`parsing/cpp.py:100-102`）。**事件提取是两条路径共用的**（`parsing/events.py` 的 `EventExtractor`，`cpp.py` 与 `python.py` 都导入它）。

**实测确认**：那 12,583 个事件里**零个 `DEREFERENCE`、零个 `WRITE`**——因为这两类来自 CFG 点。**边界精确地落在 CFG 上，不在事件上。**

**正确的表述**：**Python 有事件，没有事件之间的控制流与数据流关系；8 个查询全部建立在这些关系上，所以对 Python 全部不适用。**

**扩展路径清楚**：`parser_for_language` 是工厂函数，为 Python 补一个等价的 CFG 构建器即可。**但这是未做的工作。**

## Q6 · 38 类缺陷只做了 9 类，剩下的呢？

**先给准确数字**：矩阵 **38 类** → 登记 **13 类**（34%）→ 展开 **9 类**（24%）。

**四类未展开有明确理由**（不是遗漏）：

| 模式 | 理由 |
|---|---|
| 4.5 | OPEN/CLOSE 词表冲突 |
| 9.2 | 需 AI 侧 API 语义 |
| 9.3 | **需跨方法传播——图无跨方法控制边** |
| 9.4 | 需 catch 建模 |

**主动说出结构性限制**：**9.3 的理由是一条架构限制**——`CONTROL_REACHES` 是**方法内的**，本项目没有跨方法控制流边。**任何需要跨函数追踪控制路径的缺陷族，在当前架构下都做不了。**

**主动说出一处文档不一致**：设计文档写「36 类」，矩阵文档写「38 类」，**尚未对齐**。

## Q7 · 为什么用 SHA-256 而不是整数 ID？体积这么大怎么办？

**这是一个真实的、尚未偿还的技术债，应当直接承认。**

| 原则 | 状态 |
|---|---|
| 原则 12：持久化保留 SHA-256 stable identity | ✅ 已交付 |
| 原则 11：热拓扑使用 integer ID + CSR | ❌ **未交付** |

**两者有张力**：保 SHA 换确定性，代价是体积与遍历速度。

**实测代价**：语义层占库体积 **64.3%**（libgit2-24）/ **72.1%**（redis-50）。

**为什么选确定性**：SHA-256 stable identity 让**跨世代、跨运行的 ID 稳定**——这是增量更新与「同一实体在多次构建后仍是同一 ID」的前提。换成 runtime uint32 需要额外的映射表与持久化策略。

**诚实结论**：**这是一个可以用在设计评审里被质疑的取舍，我们选择了确定性，代价已经量化。**

→ [01](01-为什么稀疏图.md) §七、[02](02-架构与数据模型.md) §六

## Q8 · 你说确定性，为什么两次跑的 .db 文件不一样大？

**直接给边界，不含糊**：

| 断言 | 结果 |
|---|---|
| 语义内容确定（语义表字节一致，排除 `generation`） | ✅ |
| 八查询证据 ID 逐位相同 | ✅ |
| **完整 `.db` 文件字节可复现** | ❌ **412,614,656 → 413,036,544** |

**差异约 0.1%**，来自 SQLite 的页分配等内部行为，**不影响语义内容**。

**正确的表述**：「**语义内容**是确定的；**库文件字节**不是。」

## Q9 · 索引 91 秒 / 69 万行，百万行要多久？能上生产吗？

**实测吞吐**：691,462 行 / 91.1 s ≈ **7,600 行/秒**（全量重建，含解析 + 事件 + CFG/DFG + 落库）。

**外推**（基数只有**一个 10k 行样本**，且是 reference 密度偏高的库代码）：

| 代码量 | DB | update 前置内存 |
|---:|---:|---:|
| 100 万行 | 2.6 GB | **4.0 GB** |
| 300 万行 | **7.8 GB** | **12.0 GB** |

**三条必须一起说的口径**：

1. 基数只有**一个样本**，且该样本取自较早状态（源码包此后从 10,115 行涨到 16,087 行），**外推值未更新**。
2. 真实工程仓会偏高（C++ 头文件、生成代码、vendored 依赖）。
3. **量级可信，具体值不可引用为承诺。**

**主动说出未解决项**：P3（单文件 7.8 GB SQLite 破坏冻存/diff/gitignore 工作流）**仍未解决**，阶段 7（冷热拆分 + 分析副本）**未启动**。

## Q10 · use_after_free 要 124 秒，这能用吗？

**直接承认这是当前最大的性能问题。**

| 查询 | redis-50 | llama.cpp-69 | libgit2-24 |
|---|---:|---:|---:|
| `use_after_free` | **124.5 s** | 15.8 s | 5.1 s |
| `double_free` | 64.8 s | 23.7 s | 4.8 s |
| `resource_lifetime` | 7.6 s | **139.1 s** | 6.5 s |
| `taint_path` | 4.7 s | 15.3 s | 4.9 s |

**口径**：三列来自**三批不同的测量**（redis 列是受控测量；llama 列与别的库查询同时跑，偏高约 2 倍；libgit2 列是 2026-09-30 串行单进程）。**行内不可逐列精确对比，量级与「谁最慢」可以。**

**同一个查询在不同仓上差二十余倍**——主导项是 `find_paths` 的路径枚举，取决于该仓的循环结构密度。

**而且最慢的那个查询随语料移动**：redis 是 `use_after_free`，llama 是 `resource_lifetime`，libgit2 上八查询全在 **7.6 s 以内**。**这说明瓶颈在共用的枚举器上，不在某个查询里**——想靠「优化某一条查询」绕过去是走不通的。

**根因已定位**：`find_paths` 是**路径枚举器**（每个队列项自带 visited 集），用于产出证据路径是对的，用于可达性判定会指数爆炸。

**修复方案已知**（换用节点可达性 BFS / 复用扫描自己的 BFS 树）——**阶段 6 已经在 `error_handling` 上做过一次同样的修复，效果是 600+ s → 1.6 s**。**但 `use_after_free` / `double_free` 上的同类修复未实施。**

**这是一个明确的、有先例的、待办的工作项。**

→ [06](06-实验结果.md) §五、§八

## Q11 · 你的「证据」到底长什么样？

**给一条具体的**（`null_flow`，libgit2-24）：

| 字段 | 内容 |
|---|---|
| 候选 | 某行的解引用点 |
| 三态 | `ambiguous`（138 / 172 是 ambiguous，只有 34 是 `resolved`） |
| 证据路径 | 从 `malloc` 返回值到该解引用的控制流路径 |
| 淘汰记录 | `GUARDED` 14 / `PATH_DISJOINT` 2 |
| **缺失证据** | `_MISSING_NULLABILITY`——**哪些函数可能返回 NULL**（AI 侧 API 契约） |
| 缺失关系 | `CHECKS` / `DOMINATES_CHECK` / `RETURNS` |

**怎么读**：**它明确交出了「我确认不了的部分」。** 一个传统分析器只会说「第 42 行可能有空指针解引用」；本工具说的是：

> 「第 42 行有一个解引用；它的值是第 38 行 `malloc` 的返回值；从第 38 行到第 42 行之间**没有任何检查**；但**我无法判断 `malloc` 失败的可能性**，也不知道调用方是否已保证非空——**这两条是 AI 该补的**。」

→ [04](04-缺陷查询与证据包.md) §四

## Q12 · 你和 Joern / CodeQL 的区别是什么？

**设计文档 §26 明确**：**「不需要成为 Joern 的替代品。」**

| | Joern / CodeQL | 本项目 |
|---|---|---|
| 图 | 完整 CPG | **缺陷导向的稀疏图** |
| Schema 来源 | 语法产生式 | **缺陷清单（38 类矩阵）** |
| 查询 | 通用图查询语言 | **Typed Query（8 个）** |
| 不确定关系 | 通常建模为边 | **降级为证据，不造边** |
| 输出 | 查询结果 | **Evidence Bundle（含缺失证据）** |
| 对 AI 的姿态 | 供人或查询语言使用 | **为 AI 消费而设计** |

**核心差异是第 4 条**：`MAY_ALIAS` **只记候选元数据，绝不创建 `ALIAS` 边**。**这是主动选择的漏报，换「不会把猜测当事实」。**

## Q13 · AI 在里面到底做什么？是不是把静态分析的活推给 AI 了？

**先纠正前提**：**边界是明确划的，不是推卸。**

设计文档 §21 的四层分工：

| 层 | 负责 |
|---|---|
| Parser / analyzer | 语法事实 |
| Rule / extractor | 事件识别（**候选发现器，不是判定器**） |
| Graph | 确定事实与不确定证据的分层 |
| **AI** | **API 语义、上下文、最终判断** |

**关键证据**：`missing_evidence` 里明确列出「**哪些 API 的返回值必须检查**」——矩阵 9.1 **本身就写明这是 AI-required 的 API 语义**，不是图谱的活。

**词汇表文件头的自述**：

> Keywords here are CANDIDATE GENERATORS, not judges. **Nothing in this file decides that a defect exists.**

**怎么读**：**判断「这个 API 的返回值必须检查」需要的知识不在代码里。** 把它塞进图里意味着写一张永远不完整的 API 白名单。**交给 AI 是正确的分工，不是推卸。**

## Q14 · 你的评测方法可信吗？32 条样本能说明什么？

**先承认局限**：**32 条不能说明「系统的准确率」。** 项目文档对此有明确禁止：

> **不能说「precision = 0%」**：样本是 `repository × defect_key × resolution_status` 分层轮转的，12 层分 20 条，每层 1–2 条 ⇒ **分层 precision 没有统计意义**，只有合计有意义。

**那么 32 条能说明什么？——能说明 `failure_reason` 的分布。**

而**分布比比率有用得多**：

| | 阶段 4 | 阶段 6 |
|---|---:|---:|
| `identity` | 6 | 4 |
| `call_argument_loss` | 1 | **0** |
| `alias` | （隐含） | **0** |
| **`contract`** | 2 | **10（主导）** |

**这张表直接改变了路线图**：阶段 4 的 0/20 中 `needs_dfg` = **0**，推翻了原定的「阶段 5 = 直接做 DFG」；阶段 6 的 `contract` 主导说明**下一个该修的是契约层**。

**这才是评测的真正价值：不是打分，是定位下一步。**

**方法学保障**：

- **先冻结预测再实现**（探针在冻结库上跑，两次运行逐位相同）
- **对不上就如实报偏差**（2 处被证伪，已登记）
- **零未归因残差**（T2 对账逐位归因后才宣布 PASS）
- **变异验证**（把 bug 改回去，确认测试精确失败）

## 附：三条回答纪律

1. **先纠正前提，再给数字。** 大多数尖锐问题源于一个错误前提（Q1 的「做不到」、Q2 的「检测器」、Q13 的「推卸」）。
2. **主动说出代价。** 每个设计选择都有代价——`coverable_now` 全 False、`MAY_ALIAS` 不造边、SHA-256 的体积。**先说代价，比被问出来强。**
3. **数字必须配口径。** 「−97.4%」不配「95% 来自身份层」会被读成数据流的功劳；「precision 3.1%」不配「32 条分 16 层」会被读成检测器准确率。

**最重要的一句话**（建议主动说）：

> **这个工具知道自己不能做什么。** `coverable_now` 13 个模式全部为 False，是它自己说的。
